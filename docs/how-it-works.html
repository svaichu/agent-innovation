AI Compass, explained by following one idea

You know web apps, LLMs and RAG. This page adds the three things that are new here — the knowledge graph, what we mean by “agent”, and how the pieces fit — by following a single real submission, RI-0001, from the moment an employee types it to the moment it appears on the decision board.

Every number, JSON blob, graph node and code snippet on this page was read out of this repository and out of compass.db. Nothing is invented. Where the code does not answer a question, the page says so in a red box.

1Big picture

There are two web apps, a folder of text files, one SQLite database, and a batch script that joins them. Click any box.

One port or two. The two apps were built separately and originally ran on two ports with two separate logins — so a demo meant signing in twice, and you could end up logged in as two different people in two tabs. python -m compass.serve now mounts both on http://127.0.0.1:7860: the board at /, the idea chat at /intake/, behind one login. They can still be run alone on :7861 and :7860. The diagram below shows the parts, not the ports.
Click a box in the diagram

Each one tells you what it does, which file implements it, and what it would be called in an ordinary web app.

The one thing that is not like a normal web app

In a normal app, the user clicks something and the backend computes the answer right then. Here the heavy thinking happens in a batch script you run from the terminal (seed/load.py), and the result is written to the database. The board app only reads what the batch already decided. That is why the board is instant and why it needs no API key.

So the flow is not request → think → respond. It is: idea file on disk → you run python -m seed.load → rows in compass.db → board reads rows. If someone submits an idea and nobody re-runs the batch, it will not appear on the board.

2From a folder of text files to a knowledge graph

This is the part that is probably new to you. It is simpler than it sounds, and there is no machine learning in it at all.

Three words, defined once

WordWhat it means hereExample from this repo
node One thing — a person, a team, a dataset, a policy. A row in the kg_node table. employee:E17 = Luis Ortega
edge One relationship between two things, with a direction and a name. A row in kg_edge. employee:E17 --member_of--> department:support
chunk One passage of prose, kept whole so it can be searched and quoted. A row in kb_chunk. This is the part you already know as RAG. the “Not allowed” section of policies/ai-usage.md, 446 characters

So a knowledge graph is just two tables: things, and links between things. You already know how to query two tables. The value is not the technology — it is that a question like “does anyone here know how to do this?” becomes a SELECT instead of a guess.

3The intake chat: how RI-0001 got written

This is the one place in the project with a real agent in the full sense — a model that decides for itself when to call a tool, in a loop.

What runs

  • employee_interface/app.py — a Gradio chat, at /intake/ under the combined server or :7860 on its own.
  • It uses the OpenAI Agents SDK (from agents import Agent, Runner, function_tool). The model is given one tool, propose_idea, and loops until it decides to call it.
  • employee_interface/idea_store.py writes the markdown file.
This app cannot run without OPENAI_API_KEY. The page loads and login works, but typing a message raises openai.OpenAIError: Missing credentials. Unlike the evaluation side, it has no offline fallback.

What tells it which questions to ask

You would expect config/intake-questionnaire.yaml. It does not.

Verified gap. employee_interface/ imports only csv, json, re, datetime, itertools, pathlib, typing, pydantic, gradio, agents, openai. It never reads config/ and never imports compass/. Its question list is hard-coded in a Python string (INSTRUCTIONS, app.py:13–42) and its shape is the 7-field IdeaDraft model. The YAML governs the evaluation side only. The two are not wired together yet — see compass/proposals/idea-draft-8-fields.md.

The tool is what makes it an agent rather than a chatbot. The model calls it when it believes nothing is missing; the function refuses if a field is empty, and the refusal text goes back to the model as a new instruction:

And crucially, the model cannot save anything. Only the human pressing “Submit idea” calls save_raw_idea(). The file is written with open(..., "x"), so a file is never overwritten; if the ID is taken it tries the next number.

The real file it produced

Why a file and not a database row? These are the employee's own words, and the design treats them as evidence: never edited by an agent, greppable, reviewable in a pull request. Everything downstream is derived and can be rebuilt. Delete compass.db and nothing a human wrote is lost.

5The five pipeline steps

The order is not arbitrary. Step through it — every number and JSON blob below is RI-0001's real stored assessment.

Why that order. AI-fit runs before risk, because “this is not even an AI system” changes the entire regulatory conversation. Feasibility runs before scoring, because the RICE Effort number comes from the feasibility estimate instead of being invented twice.

6The risk gate, and why it never sees the score

This is the design claim the whole project rests on, so it is enforced in code rather than promised in a document.

Look at the function signature. It takes one argument: the risk payload. There is no parameter through which a business score could reach it.

7The board, and why no AI runs here

compass/app.py, served at /. Pure read-and-filter over rows the batch already wrote — which is exactly why it is fast and needs no key.

Who sees what

Three access roles, stored per employee in knowledge-base/people/capacity.csv:

RoleHow manyCan see
admin4Ranked portfolio, scoring method, review queue, and confidential pages
reviewer17Review queue; not the ranked portfolio
employee99Knowledge chat, and own submissions without scores
Authorization is server-side, not UI-side. Hiding a tab is tidiness. Every handler re-checks the role through compass/views.py, so an employee who calls the admin endpoint directly gets an error, not data. This was tested against the running server: an employee hitting the portfolio endpoint gets 401 / access-denied, not a table.

The filters, and why they are the point

The board filters on numbers the pipeline produced: cost in euros, people required, person-days, department, feasibility verdict, AI-fit verdict, “risk-clear only”, and “has open review items”. Those exist because the company's real constraints are €250,000 of tooling budget and about 60 engineering person-days a month, with 1,058 person-days already committed to 14 live projects.

Filtering is a plain list comprehension over rows already in memory (views.filter_portfolio). No model, no query to the graph, no network.

Normal-web-app comparison. This section is a normal web app: Gradio is the frontend, views.py is the controller, db.py is the data layer, compass.db is the database. The only unusual thing is that the expensive work happened earlier, in the batch.

9The knowledge chat (this part is ordinary RAG)

The “Ask the company” tab. Retrieve relevant passages, hand them to a model, cite the source. The twist is that retrieval is permission-aware.

How retrieval works

  1. The question is split into content words (stopwords and bare numbers dropped).
  2. Every allowed chunk is scored with TF-IDF — a 1970s word-counting measure of “how distinctive are the shared words”.
  3. Two boosts: ×1.5 if a query word is in the section heading, and ×(1 + 0.6 per word) if it is in the filename. The filename boost exists because ai-usage.md answers “what does the AI usage policy forbid?” even though the word “forbid” never appears in the text.
  4. The top 5 chunks are pasted into the prompt with their paths, and the model is told to cite them and never guess a number.
No embeddings anywhere. Verified: the kb_chunk table has columns id, source_path, heading, text, classification and no embedding column. There is no vector database and no embedding model call in the codebase. The _vector() function in similarity.py is a collections.Counter of word counts, not a neural embedding. If someone asks “what embedding model do you use?”, the honest answer is “none yet — that is the obvious next improvement”.

How confidential pages stay hidden

Every knowledge-base page declares a classification in its front matter, which is carried onto each chunk. A role maps to a ceiling, and the SQL only ever selects at or below it:

10Concepts: what we really use, and what we don't

Answer these exactly as written. Two of them are “no”, and claiming otherwise is the fastest way to lose an audience.

ConceptUsed?Where, precisely
RAG
retrieval-augmented generation: fetch text, put it in the prompt		 yes Two places. (1) The knowledge chat — kg/retrieve.py fetches chunks, views.ask_knowledge_base puts them in the prompt. (2) Each pipeline step gets graph facts pasted into its prompt as “the only external facts you may use”.

Embeddings

MCP
Model Context Protocol: a standard way to expose tools to a model		 no Zero matches for “mcp” across compass/, employee_interface/, config/ and seed/. Not used anywhere in the app.
Fine-tuning / training no Nothing is trained. Reliability comes from worked examples inside the prompts plus 14 labelled checks in evals/run_evals.py.
Vector / semantic search partly “Semantic” only loosely. It is lexical (TF-IDF cosine) plus a capability-signature overlap. Honest phrasing: “lexical similarity plus capability matching; embeddings are the next step.”
Why no embeddings is a real limitation, with a real number. The headline demo is that Sales' “answer tender questions” and Support's “answer repeat tickets” are the same underlying system. Pure TF-IDF scores that pair at 0.149 — far too low to link — because “tenders” and “tickets” share no words. It is only caught because a hand-written capability-tag overlap was added on top. Embeddings would catch it properly, and that is the honest “next step”.

The word “agent” means two different things in this repo

A real agent — the intake chat

employee_interface/app.py uses the OpenAI Agents SDK. The model holds a conversation, decides on its own when to call the propose_idea tool, reads the tool's refusal, and tries again. That is a loop the model drives — an agent as the industry means it.

“Agents” in compass/agents/

These are not loops. Each is a Python function that builds one prompt, makes one call, validates the JSON, and returns. compass/ does not import the Agents SDK at all. Think of them as five specialist assessors, each asked exactly one question once.

How to say it out loud: “The intake chat is a tool-using agent. The evaluation pipeline is five single-shot specialists orchestrated by plain Python, each grounded in graph facts and each with a deterministic fallback.” That is accurate, and it is a better story than pretending everything is autonomous.

Three situations route to the offline rules: no key configured, the provider errors or rate-limits, and the model returns something that is not valid JSON. Every assessment row stores which engine produced it, and the board displays that — so a rule-based verdict and a model verdict never look identical to a decision maker.

Right now every stored assessment says offline-rules-v1. No key has been configured, so everything you see on the board was produced by rules, not by a model. That is worth knowing before you describe it as AI output.

12Cheat sheet

One screen. Enough to explain the project to a teammate or answer questions after the pitch.

Employees submit ideas in a chat. A five-step pipeline turns each one into the same eight fields, checks whether AI is even the right tool, screens it against the EU AI Act, checks whether this company can actually build it, and scores it. Four admins see a ranked board. The agent recommends; people decide.

The shape

  1. Two apps, one port. python -m compass.serve → board at /, intake chat at /intake/, one login for both. The intake chat needs an OpenAI key; the board needs nothing.
  2. Ideas are files. knowledge-base/ideas/raw/RI-NNNN.md — the employee's own words, never edited by an agent.
  3. Everything else is derived into compass.db by python -m seed.load. Delete the database and rebuild; nothing human is lost.
  4. The rules are config, not code. The 8 questions, the two scoring methods and the EU AI Act decision tree are YAML in config/.

The five steps, in order and why

  1. Similarity — does another team already want this? Catches duplicates across departments.
  2. AI fit — is AI even needed, or would a script do? 2 of 43 ideas turned out to be plain integration work.
  3. EU AI Act — Article 5 prohibited / Article 6 + Annex III high-risk / Article 50 transparency as a separate flag. Every verdict cites an article.
  4. Feasibility — graph queries: who holds the skill, does the system have an API, is the data good enough, cost vs. €142k unspent, effort vs. a 1,058-day backlog.
  5. Score — configurable RICE. Business value only.

Order matters: “not an AI system” changes the risk conversation, and RICE Effort comes from feasibility rather than being guessed twice.

The two claims enforced in code

  • Risk never loses to score. risk.gate() takes one argument and the score is not it. RI-0001 ranks 3rd and is still blocked.
  • Nothing is invented. A field nobody answered is missing, not inferred. The screening cannot return “minimal risk” while a field it needs is absent — it returns “cannot tell yet” and assigns the question to a named person.

Say these exactly

If asked…Say
“Do you use embeddings?”No. TF-IDF plus capability keyword matching. Embeddings are the clearest next improvement — pure TF-IDF scored our headline duplicate pair at 0.149.
“Do you use MCP?”No. Not in the app at all.
“Did you train a model?”No. Worked examples in the prompts plus 14 labelled checks in evals/.
“Is it agentic?”The intake chat is a genuine tool-using agent. The evaluation pipeline is five single-shot specialists orchestrated by plain Python.
“Does it work without an API key?”The board and the evaluation pipeline do, on deterministic rules — that is the demo's safety net, not a feature. The intake chat does not.
“Is the AI Act screening legal advice?”No. Preliminary triage that cites articles and routes every non-minimal verdict to the Data Protection Officer (E113) and Head of Quality (E110).
